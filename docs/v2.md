# V2 features

The V2 specification (`V2_SPEC.md`) is implemented on top of the V1
contracts: V1 envelopes remain ingestible unchanged, and every V2 addition
is additive.

## Event envelope v2

`schema_version: "2.0"` adds three optional fields:

- `entities` — `{"role": "namespace://path"}` canonical identifiers, e.g.
  `{"asset": "asset://silver/samples", "run": "run://dagster/01J…"}`
- `tags` — searchable string labels
- `contract` — `{"name", "version", "schema_id", "schema_hash"}` binding
  the event to a typed `EventContract`

New categories: `metric`, `lineage`, `insight`, `incident`. All V1
categories and fields are unchanged.

## Canonical identifiers

`observe_core.identifiers` builds namespaced URIs:

```python
asset_id("silver", "samples")  # asset://silver/samples
run_id_for("dagster", run_id)  # run://dagster/<id>
iceberg_id("cat", "ns", "tbl")  # iceberg://cat/ns/tbl
branch_id("nessie", "run-abc")  # branch://nessie/run-abc
model_id("dbt", "silver_samples")  # model://dbt/silver_samples
source_id("dlt", "labware")  # source://dlt/labware
snapshot_id_for("tbl", snap)  # snapshot://tbl/<snap>
service_id("trino")  # service://trino
```

The SDK integrations set these automatically; correlation-field-only
events are mapped to the same identifiers server-side.

## State engine

Canonical events are the source of truth. The observer derives, and can
always rebuild, these projections:

- **runs** — status, timing, error counts, touched assets
- **entities** — registry of every canonical identifier seen, with
  `first_seen_at`/`last_seen_at` and provenance (`derived_from` event
  IDs, rule id/version)
- **relationships** — typed edges (`writes_to`, `produces`, `executes`,
  `validates`, `promotes`, …), each carrying `method` (`explicit` /
  `inferred`), `confidence`, and provenance
- **assets** — materialization status, freshness, row/byte totals
- **branches** — WAP/Nessie lifecycle state in entity attributes
  (`open` → `promoted` / `rejected` / `cleaned`, validation results,
  last commit)

Rebuild everything, or one run's scope:

```bash
phlo-observer rebuild-projections
phlo-observer rebuild-projections --run <run_id>
phlo-observer reprocess --since 2026-09-01T00:00:00Z
```

A scoped `--run` rebuild replaces only that run's row, merges its entity
and edge contributions into existing state, and re-derives each asset it
touched from the asset's *full* event history — a shared asset is never
regressed by rebuilding one of the runs that touched it. Insights,
incidents and baselines are only rebuilt by the unscoped form.

Full rebuilds preserve existing insight and incident IDs, operator lifecycle
states, and lifecycle timestamps. Transitions are recorded separately from
derived tables; historical rows whose evidence has expired remain subject
to the existing retention policy rather than disappearing during rebuild.

Reconstruction must establish a unique correspondence between old and new
lifecycle episodes. If replay would merge or split existing episodes, the
command refuses and rolls back the entire rebuild. This can occur when
historical acknowledgements separated findings that canonical event replay
would combine. Investigate that history rather than deleting decisions to
force a rebuild. Transitions and retention wait behind the rebuild lock.
Database backups preserve lifecycle records; event-only archives do not
contain operator decisions.

`reprocess` is a surgical companion: it re-folds a `received_at` window
of canonical events through `apply_event`, merging into entity/asset/
edge state. It does not re-derive run rows, insights or baselines.

## Baselines and insights

`observe_baselines` keeps a rolling median/MAD/percentile-band/EWMA per
`(entity, metric)` — run duration, rows in/out, bytes, retry counts, and
similar measures. Deterministic rules in `phlo_observer.insights` raise
`observe_insights` rows: duration > 2× rolling median, row-count
threshold breaches, recurring quality-check failures, and similar.
Every insight carries `rule_id`, `rule_version`, `severity`, and
`evidence_event_ids`.

Insight lifecycle: `open` → `acknowledged` / `resolved` / `suppressed` /
`expired`. Events resolve matching insights automatically; operators can
transition manually via `POST /v2/insights/{id}/transition`. Transitions
are a checked state machine — `expired` is terminal and illegal moves
return 409; same-state transitions stay idempotent.

## Incidents

Rule-created insights group into `observe_incidents` by shared run,
root error, asset, service, deployment, or time window. Incidents have
`open` / `acknowledged` / `resolved` / `suppressed` states via
`POST /v2/incidents/{id}/transition`. Leaving `resolved` clears
`resolved_at` so a reopened incident never carries a stale stamp.

## Query API

```text
GET  /v2/runs/{id}                 run projection + entities
GET  /v2/runs/{id}/timeline        phase-grouped events
GET  /v2/runs/{id}/failures        failure events with evidence IDs
GET  /v2/runs/{id}/changes         changes in the window before the run
GET  /v2/runs/{id}/impact          downstream entities via edges
GET  /v2/runs/{id}/investigate     deterministic investigation bundle
POST /v2/query/compare-runs        side-by-side comparison
GET  /v2/assets/{id}               asset projection
GET  /v2/assets/{id}/health        status + freshness SLA + open insights
GET  /v2/assets/{id}/history       event history
GET  /v2/assets/{id}/lineage       upstream/downstream edges
GET  /v2/entities[?type=]          entity registry
GET  /v2/insights[?state=&entity=]
GET  /v2/incidents[?state=]
GET  /v2/incidents/{id}
GET  /v2/events/{id}/provenance    which projections an event fed
GET  /v2/search?q=                 Postgres ILIKE over name, error
                                   message, asset, table, service
GET  /v2/stream                    SSE notification channel
GET  /v2/schemas                   registered contract schemas
POST /v2/schemas                   register a schema
GET  /v2/analyses                  recorded agent analyses
POST /v2/analyses                  record an analysis (ingest scope)
```

## Typed query client

```python
from observe_query import ObserverClient

client = ObserverClient("http://localhost:8080", token="…")
run = client.run("01J…")
run.failures()  # failure events with evidence IDs
run.recent_changes()  # changes before the run
run.affected_downstream()  # impact via edges
run.investigate()  # full investigation bundle
run.compare("01J…")  # vs another run
client.asset_health("asset://silver/samples")
client.incidents(state="open")
```

The client is read-only by default; `observe_query.tools` maps the
agent-tool surface (`get_run`, `get_failures`, `get_lineage`, …) onto it.

## Stream

`GET /v2/stream` is an SSE channel for change notifications —
`run.changed`, `insight.opened`, `incident.updated`. Notifications are
hints, not state: clients refetch the authoritative endpoints.

## Alerting

`PHLO_OBSERVER_ALERT_WEBHOOK_URLS` (comma-separated) POSTs insight and
incident notifications to external webhooks. Delivery is fire-and-forget
and bounded — a slow endpoint never blocks ingest. Vendor integrations
(Slack, Teams, email) live outside the observer.

## Security scopes

- `PHLO_OBSERVER_INGEST_TOKENS` — write events (`observe:ingest`)
- `PHLO_OBSERVER_READ_TOKENS` — query APIs (`observe:read`)
- `PHLO_OBSERVER_ADMIN_TOKENS` — transitions, quarantine, schemas
  (`observe:admin`); **required** once any other token surface is
  configured — admin powers are never inherited from read tokens

Dev mode (no tokens configured on any surface) stays open. The moment
any token exists, *every* unset list fails closed: configuring only
`INGEST_TOKENS` does not leave the query APIs anonymous, and
configuring only `READ_TOKENS` does not leave event ingest open.
`PHLO_OBSERVER_AUTH_OPTIONAL_DEV=false` requires all three scopes.

## Quarantine and replay

Payloads that fail normalization land in `observe_ingest_failures` with
the original payload retained where policy allows:

```text
GET  /v2/admin/quarantine                 list failures
POST /v2/admin/quarantine/{id}/replay     re-run the adapter
```

Digest-only payloads report as non-replayable — the original bytes are
gone, so replay is refused rather than fabricated.

## Archive and restore

```bash
phlo-observer archive events.jsonl --since 2026-01-01 --batch 1000
phlo-observer restore events.jsonl
```

Archives contain the normalized envelope per line; `restore` re-ingests
through the canonical path, so dedup and projections behave identically
to live ingest.

## Operator CLI

```bash
phlo-observe doctor                  # local SDK config + runtime health
phlo-observe schemas list            # registry contents
phlo-observe schemas validate f.json # check a local envelope file
phlo-observe events tail --follow    # newest events, polling
phlo-observe run show <id>           # run projection
phlo-observe run compare <a> <b>     # side-by-side
phlo-observe incident show <id>
phlo-observe replay <failure_id>     # quarantine replay (admin)
phlo-observe benchmark --events 500  # ingest/query latency
```

`OBSERVER_URL` selects the observer; `OBSERVE_READ_TOKEN` /
`OBSERVE_ADMIN_TOKEN` / `OBSERVE_INGEST_TOKEN` authenticate.

## Agent analysis provenance

LLM-generated analyses are recorded in `observe_agent_analyses` with the
model, prompt template version, evidence event IDs, and output — every
generated conclusion stays traceable to its inputs.

## High availability

The observer is a stateless HTTP service on a shared PostgreSQL database,
so multiple instances can run behind a load balancer:

- ingest nodes hold no local critical state — every write lands in
  Postgres, and dedup makes re-ingest idempotent;
- run/entity projections serialize through row locks, so concurrent
  instances folding the same run cannot lose updates;
- the retention job takes a Postgres advisory lock
  (`pg_try_advisory_xact_lock`), so only one instance cleans up at a
  time and the rest skip the pass;
- the SSE hub is per-instance by design — clients receive events
  ingested by the instance they are connected to.

## Disaster recovery

- **Backup**: standard PostgreSQL backup (`pg_dump`/`pg_basebackup` or a
  managed-service snapshot). All durable state lives in the database.
- **Restore**: restore the database, then run `phlo-observer migrate` and
  start the service. Derived state can be regenerated at any time with
  `phlo-observer rebuild-projections` — canonical events are the source
  of truth.
- **RPO** is determined by the database backup schedule; the observer
  adds no additional data-loss window.
- **RTO** is database restore time plus service start; projections do not
  need to be rebuilt before serving ingest.

The `archive`/`restore` commands complement database backup for
long-horizon event retention in JSONL form.
